# Wishmaker Jirachi: a real hunt through BizHawk and Dolphin

Status: spike done, 2026-10-24 to 25; implemented by the [Wishmaker Jirachi spec](../specs/wishmaker-jirachi.md) (epic #163, 2026-10-25, plan phase 7), with the choices recorded in [decisions](../decisions/wishmaker-jirachi.md). The bot differs from this write-up in three places: the GBA reset is the posted variant (Down four times and a Return key-down to the popup), not UI Automation, which stays the fallback ("GBA timing" row); the GBA ROM and saves path go on the command line with `-C`, which works on 2609a and is not persisted, so the last open point is settled; and the save step confirms the start menu is live by a cursor probe, with the spike's waits between held presses ("Save twice" row). The rows and open points below stay as the spike's record.

## What was proved

A full hunt cycle runs unattended with no edited bytes anywhere: BizHawk loads the base save, continues the game, plays for a random stretch, saves in-game, flushes and closes; Dolphin boots the Colosseum Bonus Disc with that save on the integrated GBA, the script drives the Jirachi menu and reboots the GBA at the "turn on the power" prompt; the GBA save comes back with Jirachi in slot 1 and the script parses it, predicts the PID from the save's checksum, and logs the cycle. Six such cycles ran in a row at 95 to 110 seconds each, every result matching its prediction. The result save loads in BizHawk with ApiHawk attached and the party reads from the existing RS addresses.

Two facts shape the hunt:

1. **The Jirachi is a function of the save.** The disc seeds Jirachi from the 16-bit checksum of section 0 (trainer data) in the save's first block (file offset `0x0000` to `0xDFFF`), whichever block the game would load. The PID is the Gen 3 LCRNG run from that seed: first output is the high half, second the low half. This was verified on nine seeds, including a crafted save that produced the shiny PID `987ED636` from seed `ECDD` on the first try, and a save whose live block carried a different seed that the disc ignored.
2. **The game alternates blocks on each save.** A save that lands in the second block leaves the first block, and so the Jirachi, unchanged. Cycle 2 of the first real run proved it: same seed, same PID as cycle 1. The hunt therefore saves until the first block holds the newest counter (one or two in-game saves), and a duplicate is detectable from the file before Dolphin starts.

## The seed

Section 0 is 3884 bytes of data plus a footer at `0xFF4` (id, checksum, signature `0x08012025`, counter). The checksum is the 32-bit sum of the data words folded to 16 bits. Play time sits at `0x0E` (hours `u16`) and `0x10` to `0x12` (minutes, seconds, frames), so hours and frames move the high half-word and minutes and seconds the low one. The nine shiny seeds for this Jirachi (`353D`, `3D60`, `7236`, `7360`, `9359`, `A030`, `CF37`, `ECDD`, `F500`; sources: [pokemonrng.com](https://www.pokemonrng.com/emulator-rs-wishmaker/), [shinyJirachiCalc](https://github.com/resonancellc/shinyJirachiCalc)) matched the LCRNG rule above.

Odds for a real hunt are not 9 in 65536 per cycle. The seeds from one base save sit in a band: all 35 real cycles so far (a one-hour soak of 23 plus the earlier runs) landed between about `DB00` and `0E00`, a band roughly 13k wide, with no repeats. That is what play time predicts (minutes and seconds in the low half-word, hours and frames in the high one; the band drifts by one per hour of play). Two of the nine shiny seeds, `ECDD` and `F500`, lie inside it, so the per-cycle chance is about 2 in 13k, roughly 1 in 6500: about 11 days at 155 s a cycle, comparable to the naive 1 in 7281. The other seven shiny seeds are out of reach from this save short of hundreds of hours of play time; a different base save (different trainer data) has a different band.

## ROM revision

The spike ran on Sapphire USA rev 0 (`AXPE`, header revision 0) through the soak, then on the rev 2 ROM the bot hunts with (`Pokemon - Sapphire Version (USA, Europe) (Rev 2).gba`) for two further cycles with the same base save, the same scripts and the same addresses. Both passed: the rev 0 save continued on rev 2, the start-menu bytes at `0x0202E8FC` to `0x0202E8FE` read the same menu, the disc accepted the cartridge, and both PIDs matched their predictions. Cycle time was 171 s, within the usual spread. This agrees with the note in `RsPointerService` that the EWRAM and IWRAM symbols are identical across RS revisions; the seed and the Jirachi come from the save and the disc, not the ROM.

## Soak

One hour unattended on 2026-10-24: 23 cycles, 23 Jirachi, no stalls, no retries, every PID matching the prediction from block A, 152 to 167 s per cycle (mean 159 s), 14 A presses to the power prompt every time, no repeated seed. Both emulators were restarted every cycle. The base save's counter went from 34 to 78.

## What a bot needs

- A Dolphin launcher beside the BizHawk one, the DSU pad server (a UDP socket and an 84-byte frame), the MEM1 mapping reader, the Bonus Disc state machine on the four bytes above, the UI Automation GBA reset, and a per-cycle copy of the base into Dolphin's `-2.sav` path. Nothing in the Dolphin half reads the screen, needs keyboard focus, or depends on where a window is. Every wait is a memory value or a file change with a timeout that stops and reports.
- The in-game save step as above, with the flush poll until all 14 sections are new, and the save-again rule for the first block. The section walk is 30 lines of pure code next to `Gen3SaveFile`.
- A parse of the result (PKHeX.Core, or `Gen3PokemonParser` on the raw 100-byte slot) and the LCRNG prediction from the first block's checksum as a consistency check; a mismatch means the disc read something else and the cycle should stop and report.
- An encounter log entry per cycle; the base save carried forward; the result save kept and loaded in BizHawk on a shiny.

## Open points

- The disc's own requirements were not probed: no Pokédex, no free slot, or a save that already received Jirachi.
- Why the `GBA Core/Reset` hotkey never fires. The UI Automation invoke by item name replaces it and depends on neither focus nor item order; a Dolphin fork with a command socket, like ApiHawk, would be the cleaner long-term answer and the owner already maintains an emulator fork.
- The menu cursor byte at `0x80D0ED38` held its address on seven boots of Dolphin 2609a; another Dolphin version or a different disc revision has not been tried.
- A "waiting for A" byte for the instruction screens, so the presses are gated per screen instead of once per 1.5 s until the power prompt.
- Keeping Dolphin running between cycles (the disc offers "back to the beginning") would save about 15 s; the GBA save would need Unload ROM, replace file, Load ROM.
- How much the RTC fields in section 0 widen the reachable seed band, and whether BizHawk's RTC should run.
- Dolphin's config edits live in the user's `Dolphin.ini`; the bot should pass them with `-C` on the command line instead.
